# Choose Godot, then prove it on Windows

Build the trainer in **Godot 4.7.x** (4.7.2 is the current stable release), mostly in statically typed GDScript, and spend the first week on a small test build that you run on your Windows PC before writing gameplay at scale. Two requirements decide the choice, and neither is about runtime speed. First, Godot imports your `.glb` bots, runs tests, renders screenshots and exports a Windows `.exe` inside a headless Linux container with no GPU and no account (all verified in this project's container), while Unity needs a roughly 9 GB install, your Unity login stored as a secret, and a GPU before it draws a single frame. Second, Godot's importer turns each bone-parented `HB_` hitbox into a bone-attached node carrying its glTF extras, where Unity's glTF package needs custom code just to read extras. At runtime the engines are closer than their reputations suggest, since both read raw Windows mouse counts and both let you turn off V-Sync and shorten the render queue, but Godot still leads: it shipped a benchmarked fix for 4–8 kHz mice in August 2026 that Unity still lists as a known issue, and its controller layer delivers raw sticks and gyro that Unity does not support on PC. Unity's real advantages are precedent (Aimlabs runs on it), a far larger asset store, much more C# training data for the agent, batched raycasts and a third-party Reflex plugin, yet none of them outweighs the workflow gap for a game an agent builds in a container. Godot's main risks are a reported menu-freeze bug in 4.7.2, the agent slipping into outdated Godot 3 code, and the absence of published input-latency measurements for either engine. The seven first-week tests at the end of this report are designed to catch all three.

## Godot wins six of eleven requirements, including the two that decide it

The requirements do not carry equal weight. No engine ships Apex-style movement, projectile ballistics, recoil patterns, aim assist or stick response curves, so all of them are custom code in either engine, and the choice only changes which open-source starting points exist. The engine matters most where the game touches the platform. That means four things: how mouse and controller input reach your code, how quickly a finished frame reaches the screen, how your existing bot files come in, and how an agent with no screen and no GPU builds and checks the game. Godot leads on all four, although its latency lead comes with caveats covered below. Unity's clear wins are in the ecosystem rows. Cost is a draw while revenue stays under $200K.

| Requirement | Godot 4.7.x | Unity 6.x | Edge |
|---|---|---|---|
| Raw mouse input, exact Apex sensitivity | Raw counts via `screen_relative`, summed without loss; behaviour can be checked in the engine source | Source code says `Mouse.delta` comes from Windows raw input; forum reports of rounding to whole pixels unresolved | Godot, slight |
| 1–8 kHz mice, 144–500 Hz monitors, low latency | 8 kHz fix in 4.7.2 with published benchmarks; possible menu-stall regression; frame queue cannot go below 2 | 8 kHz slowdown still listed as a known issue; queue can go down to 1; third-party Reflex plugin (URP only) | Godot |
| Controller, aim assist, response curves | SDL3: raw linear sticks, built-in gyro API (experimental), Steam Input handle | XInput/HID; default 0.125–0.925 stick deadzone; no gyro on PC | Godot |
| Source/Titanfall movement for player and bots | SUCC controller (MIT, maintained, Godot 4.6+) | Fragsurf port (MIT, last commit 2020) | Godot, slight |
| Projectiles with travel time and drop | One `intersect_ray` call per bullet, only during the physics step | Batched, multithreaded `RaycastCommand` | Unity, slight |
| Recoil patterns | Pure code; an open-source template already has spray profiles | Pure code | Tie |
| Animated `.glb` bots with hitbox extras and sidecar | Extras become node metadata; bone attachments generated automatically | Extras need add-on code; imported Mecanim clips need manual wiring; the sidecar is the practical route | Godot, clear |
| Solo team, no budget, Steam, Windows first | MIT, $0 at any revenue; GodotSteam | $0 below $200K revenue plus funding, then $2,310 per seat per year; Steamworks.NET | Tie |
| AI agent in a headless Linux container | 78 MB binary; tests, screenshots and `.exe` export verified | 4.5 GB download; licence secrets; no rendering without a GPU; no Windows IL2CPP builds from Linux | Godot, decisive |
| Quality of the agent's code | Small GDScript corpus; drift into Godot 3 syntax, caught by the parser | Huge C# and Unity corpus | Unity |
| Precedent and ecosystem | Hobby aim trainers; one hit solo FPS | Aimlabs, Tarkov, BattleBit; about 80K store assets | Unity |

The weighting matters more than the tally. The agent row decides the question because it affects every working day. Each change the agent makes is either verified in under a second or waits on an editor boot and a licence check. Each visual check either happens inside the container or waits for you. The bot-file row decides how much glue code stands between your finished art and the first target you can shoot. Unity's three wins are real, but they make development more comfortable; none of them covers a requirement that Godot fails to meet.

## The agent's container rules out a smooth Unity workflow

Most of this code will be written by an agent in a Linux container with no GPU and no display, and that environment favours Godot more than any runtime benchmark does. The research team ran Godot inside this project's container (Ubuntu 24.04, 4 cores, no GPU) and timed each step of the agent's edit-run-check loop. The Unity column comes from Unity's own documentation, because Unity's size and licence requirement kept the team from installing it there.

| Step in the agent's loop | Godot 4.7.2, measured in this container | Unity 6.3 LTS, from Unity's docs |
|---|---|---|
| Get the engine | 78 MB zip, one 146 MB binary, no installer | 4.54 GB download, 8.73 GB installed, or a 5–6 GB Docker image |
| Activate a licence | Nothing to activate | Personal licence file created in the Unity Hub GUI, plus your email and password stored as secrets |
| Check code for errors | 0.17 s parse check | Script compile plus domain reload after each change |
| Run tests | 0.27 s for a headless test that loads a scene containing a bot `.glb` | `-batchmode -runTests`, which pays the editor boot and licence activation on every run |
| Render a screenshot without a GPU | 10.2 s (OpenGL on Mesa llvmpipe), 23.9 s (Vulkan Forward+ on Mesa lavapipe) | `-nographics` creates no graphics device; software rendering is unsupported and untested |
| Build for Windows from Linux | 6.1 s, producing a 110 MB `.exe` | Mono scripting backend only; IL2CPP needs a Windows machine with Visual Studio |
| Write scenes as text | A hand-written `.tscn` loaded and rendered | UnityYAML with numeric fileIDs and `.meta` GUIDs, created through editor scripts |

Godot's Linux editor is a **single 78 MB download that unzips to one executable**. It runs with `--headless`, which the docs describe as "required on platforms that do not have GPU access" ([Godot download](https://godotengine.org/download/linux/), [Godot command-line docs](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html)). The Windows export templates are a one-time 1.28 GB download. After that, a single `--export-release` command produced a valid 64-bit Windows executable in 6.1 seconds. It has not yet been launched on Windows; that is test 2 below. Unity 6.3 LTS for Linux is a **4.54 GB download that installs to 8.73 GB**, plus 385 MB for the Windows Mono build module ([Unity release API](https://services.api.unity.com/unity/editor/release/v1/releases?version=6000.3.25f1&platform=LINUX&architecture=X86_64&limit=1)). Unity supports its Linux editor only on desktop Ubuntu with NVIDIA or AMD GPUs and a GNOME desktop ([Unity system requirements](https://docs.unity3d.com/6000.3/Documentation/Manual/system-requirements.html)). In a container, the supported mode is `-batchmode -nographics`, in which "Unity doesn't initialize the graphics device" ([Unity command-line arguments](https://docs.unity3d.com/6000.3/Documentation/Manual/EditorCommandLineArguments.html)). That rules out screenshots, so the agent could never look at what it built. Godot cannot render in `--headless` mode either. Under a virtual display (Xvfb) with Mesa's software renderers, however, it produced correct 1280×720 frames of the bot model with shadows and sky.

Licensing is the second obstacle. Unity's manual says plainly that command-line activation does not apply to Personal: "To activate a license for Unity Personal, log in to the Unity Hub" ([Unity licence docs](https://docs.unity3d.com/6000.3/Documentation/Manual/ManagingYourUnityLicense.html)). The documented CI workaround has three steps. You create a licence file in the Hub on your own PC. You then store that file, your Unity email and your **Unity password** as secrets in the agent's environment ([GameCI activation](https://game.ci/docs/github/activation)). Every fresh container then reuses those credentials. Unity's official MCP server does not solve this. It connects to a running editor with a GUI, waits for someone to click Accept, and requires a Unity Cloud project plus a paid or trial AI subscription ([Unity MCP blog](https://unity.com/blog/unity-ai-mcp-how-to-get-started)). A standalone Unity CLI with headless service-account login exists, but it is still on a **beta** channel ([Unity CLI blog](https://unity.com/blog/meet-the-unity-cli)). Unity 7 promises a "free MCP, CLI, and API built in", with a preview due in December 2026 and full release in Q1 2027 ([Unite Seoul 2026 recap](https://unity.com/blog/unite-seoul-keynote-2026-recap)).

File formats widen the gap. Godot scenes are INI-like text files ([TSCN format](https://docs.godotengine.org/en/stable/engine_details/file_formats/tscn.html)). During the research, the agent wrote a roughly 50-line scene by hand that placed the repo's `dummy_medium.glb` next to a light and a floor, and Godot loaded and rendered it without modifying the file. Unity scenes are multi-document YAML files built from numeric class IDs and fileID anchors that point at GUIDs stored in generated `.meta` files. Losing a `.meta` file breaks every reference to that asset ([UnityYAML format](https://docs.unity3d.com/6000.3/Documentation/Manual/FormatDescription.html), [Unity asset metadata](https://docs.unity3d.com/6000.3/Documentation/Manual/AssetMetadata.html)). In practice, an agent working in Unity would build scenes through C# editor scripts run in batch mode, and would pay an editor boot every time. Finally, Unity on Linux can build Windows games only with the **Mono backend**. The faster IL2CPP backend needs Visual Studio's C++ tools on a Windows machine, and the Linux editor offers no Windows IL2CPP module ([Unity system requirements](https://docs.unity3d.com/6000.3/Documentation/Manual/system-requirements.html), [Unity release API](https://services.api.unity.com/unity/editor/release/v1/releases?version=6000.3.25f1&platform=LINUX&architecture=X86_64&limit=1)). Mono builds are fine for testing. An IL2CPP release build would need a Windows CI runner with its own licence activation.

## Both engines read raw mouse counts; only Godot has fixed 8 kHz mice

### Exact sensitivity depends on one property name

To match Apex's sensitivity, the engine must deliver every mouse count, unscaled and unrounded. The trainer's own formula (counts × degrees per count × sensitivity) then does the rest. In Godot, that path is both documented and readable in the source. While the mouse is captured, Windows raw-input (`WM_INPUT`) counts go straight into `InputEventMouseMotion.screen_relative` ([display_server_windows.cpp](https://github.com/godotengine/godot/blob/master/platform/windows/display_server_windows.cpp)). When several events arrive in one frame, Godot adds them together instead of dropping any ([input_event.cpp](https://github.com/godotengine/godot/blob/master/core/input/input_event.cpp)). The docs warn that the similarly named `relative` property is **scaled by the window's content scale factor**, so "mouse sensitivity will appear different depending on resolution", and they recommend `screen_relative` for aiming ([InputEventMouseMotion docs](https://docs.godotengine.org/en/stable/classes/class_inputeventmousemotion.html)). The raw path exists only in captured mode. A visible cursor goes through ordinary Windows mouse messages, which the Windows pointer-speed setting affects.

Unity's Input System also reads raw input. The source comment on `Mouse.delta` says "On Windows, delta originates from RAWINPUT API", and adds that the value "might not update every frame, particularly if your project is running at a high frame rates" ([Mouse.cs](https://github.com/Unity-Technologies/InputSystem/blob/develop/Packages/com.unity.inputsystem/InputSystem/Runtime/Devices/Mouse.cs)). A Unity forum thread claims the delta comes in whole pixels, which would make tiny high-DPI movements disappear ([Unity Discussions](https://discussions.unity.com/t/new-input-system-get-raw-mouse-delta-from-wm_input/857382)). The source comment contradicts that claim, and the research found no primary Unity documentation that settles it. Unity is very probably fine here as well; the difference is that Godot's behaviour can be confirmed from its own code and docs.

### 8 kHz mice break Windows games, and Godot has a measured fix

High-polling mice are where the engines separate. Windows generates legacy mouse messages alongside raw input even when a game only wants raw input. Godot's developers found that "on most CPUs, this limit is generally somewhere between 1 kHz and 2 kHz. If your mouse sends much more updates than this limit, the framerate can drop to the single digits" ([Godot blog](https://godotengine.org/article/fixing-high-polling-rate-mice-on-windows/)). **Godot 4.7.2, released on 18 August 2026, fixed this.** It now reads raw input in buffered batches and sends legacy mouse messages at most once per frame ([Godot 4.7.2 release](https://godotengine.org/article/maintenance-release-godot-4-7-2/)). The published benchmark used a Ryzen 9 9950X3D and an RTX 5090 at 1080p on a 480 Hz monitor:

| Test (8 kHz mouse, moving fast) | Godot 4.7.1 | With the fix (4.8.dev3, same code as 4.7.2) |
|---|---|---|
| Captured mouse, V-Sync off | under 1 FPS | 1,703 FPS (0.59 ms per frame) |
| Visible cursor, V-Sync off | 173 FPS | 1,103 FPS |
| Captured mouse, V-Sync at 480 Hz | under 1 FPS | 477 FPS (2.10 ms per frame) |

The 1% low frame rate improved 45.8-fold ([Godot blog](https://godotengine.org/article/fixing-high-polling-rate-mice-on-windows/)). There is a catch. Issue #122779, opened on 24 August 2026, reports **multi-second freezes in 4.7.2 when the cursor is visible**, which is exactly the menu case, and says they did not happen in 4.7.1. The reporter suspects the new code, and the issue had no response from maintainers when the research was done ([#122779](https://github.com/godotengine/godot/issues/122779)).

Unity has not fixed the equivalent problem. Forum reports, which the researchers could only see as search snippets, describe the editor's main-thread time rising from about 3 ms when idle to 30 ms at 4 kHz and 100 ms at 8 kHz. The same reports describe **freezes of about half a second at 8 kHz in standalone builds**, and quote Unity staff blaming the same Windows message translation ([Unity Discussions](https://discussions.unity.com/t/performance-degradation-while-using-mouse-with-high-polling-rate-any-known-engine-version-without-the-problem/1508487?page=2)). The 6000.7.0b2 release notes list "Play Mode framerate drops significantly when moving a high-polling-rate mouse" (UUM-142550) as a known issue, and snippets say it is still listed for the current 6000.6.4f1 release ([Unity 6000.7.0b2](https://unity.com/releases/editor/beta/6000.7.0b2), [Unity 6000.6.4f1](https://unity.com/releases/editor/whats-new/6000.6.4f1)). Even read-only access to Unity's engine source is an Enterprise feature ([Unity pricing](https://unity.com/products/pricing-updates)), so a Unity project has to wait for Unity to fix bugs like this. A Godot project can patch its MIT-licensed engine itself if it has to.

### Latency comes down to settings in both engines

**Nobody has published a controlled click-to-photon comparison of Unity 6 and Godot 4**; the research turned up only opinion pieces. The two engines work in much the same way. Both sample input once per frame before game logic runs, and both allow V-Sync off and uncapped frame rates. Godot offers several V-Sync modes and a `max_fps` cap. It also supports a two-image swapchain ("Double-buffering may give you the lowest lag/latency"). For variable-refresh (VRR) monitors it documents a frame-cap formula: **224 FPS at 240 Hz, 324 at 360 Hz and 416 at 480 Hz**. That cap adds input lag "usually less than 1 ms greater" than V-Sync off, without tearing ([ProjectSettings](https://github.com/godotengine/godot/blob/master/doc/classes/ProjectSettings.xml), [Godot jitter and input-lag docs](https://docs.godotengine.org/en/latest/tutorials/rendering/jitter_stutter.html)). The same docs recommend exclusive fullscreen on Windows to reduce input lag, and warn that physics interpolation "improves smoothness but increases latency". Mouse-look therefore belongs in the per-frame `_process` callback, never on the physics tick.

Unity has two latency settings that Godot lacks. First, Unity's `QualitySettings.maxQueuedFrames` can be set to 1, which "essentially disable[s] pipelining" ([Unity docs, older version](https://docs.unity3d.com/400/Documentation/ScriptReference/QualitySettings-maxQueuedFrames.html)). Godot's equivalent, `frame_queue_size`, has a hard-coded minimum of 2. The author of a Godot feature proposal, who keeps external latency measurements, says that minimum adds unwanted latency in action games ([godot-proposals #11200](https://github.com/godotengine/godot-proposals/issues/11200)). Second, a $4.99 "Reflex Low Latency Plugin for Unity" is on the Asset Store; it supports URP only, and its publisher could not be confirmed ([Asset Store listing](https://assetstore.unity.com/packages/tools/utilities/reflex-low-latency-plugin-for-unity-378338)). Godot has no Reflex or Anti-Lag support, and the proposal to add it is still open. An aim trainer runs far above the monitor's refresh rate with V-Sync off, so the GPU is rarely the bottleneck and Reflex gains less there. The queue-depth difference is the one worth measuring, and test 5 below measures it. Godot also has open frame-pacing reports, including one about visual input delay in exclusive fullscreen with V-Sync on ([#77596](https://github.com/godotengine/godot/issues/77596)); the research did not check their status.

## Controllers, movement and bots favour Godot; projectiles and recoil are a wash

### Raw sticks and gyro come built in through SDL3

Simulated Apex aim assist and response curves are custom code in both engines. What matters is getting clean, unprocessed stick values to shape. Since version 4.5, Godot has used the **SDL3 library for controllers** on Windows, macOS and Linux ([Godot controller docs](https://docs.godotengine.org/en/stable/tutorials/inputs/controllers_gamepads_joysticks.html)). Its SDL driver maps stick axes linearly to the range −1 to 1 with no deadzone at that layer. Deadzones apply only if you route input through Godot's input actions ([joypad_sdl.cpp](https://github.com/godotengine/godot/blob/master/drivers/sdl/joypad_sdl.cpp), [Input class reference](https://github.com/godotengine/godot/blob/master/doc/classes/Input.xml)). Godot 4.7 added a built-in gyro and accelerometer API with calibration. It is marked experimental, was tested on a Switch Pro controller, and the DualSense is "expected compatible" ([PR #111679](https://github.com/godotengine/godot/pull/111679)). The 4.8 development builds add gyro auto-calibration ([4.8 dev4](https://godotengine.org/article/dev-snapshot-godot-4-8-dev-4/)). The driver also reports each pad's Steam Input handle.

Unity reads Xbox pads through Microsoft's XInput API and the DualSense through HID ([Unity Xbox controller docs](https://github.com/Unity-Technologies/InputSystem/blob/develop/Packages/com.unity.inputsystem/Documentation~/gamepads-xbox.md)). However, every gamepad stick ships with a `stickDeadzone` processor that defaults to **0.125–0.925** ([Gamepad.cs](https://github.com/Unity-Technologies/InputSystem/blob/develop/Packages/com.unity.inputsystem/InputSystem/Runtime/Devices/Gamepad.cs), [InputSettings.cs](https://github.com/Unity-Technologies/InputSystem/blob/develop/Packages/com.unity.inputsystem/InputSystem/Runtime/InputSettings.cs)), and you would have to remove it before applying Apex-style curves. More limiting still, Unity's own device list says "Unity doesn't support the gyro or accelerometer on PS4/PS5 controllers on platforms other than the PlayStation consoles". It also says DualSense rumble and lightbar control do not work over Bluetooth ([Unity supported devices](https://github.com/Unity-Technologies/InputSystem/blob/develop/Packages/com.unity.inputsystem/Documentation~/supported-devices-reference.md)). Gyro aiming in Unity therefore means bringing in a third-party native library.

### Neither engine ships Apex movement

Open-source code for Source-style air acceleration, friction and bunny-hopping exists for both engines. Apex's own mechanics, however, are **custom work in either engine**: slides with a speed boost and decay, slide-jumps and tap-strafes. Godot's best starting point is **SUCC**, the MIT-licensed controller from the Steam game *SurfsUp*. It is written in typed GDScript for Godot 4.6+ and was last updated in August 2026. It ports Source's `ClipVelocity`, swaps its whole "feel" through preset files such as `source.tres` and `quake.tres`, and ships a test map with slide and bunny-hop lanes ([SUCC](https://github.com/bearlikelion/SUCC), [succ.gd](https://github.com/bearlikelion/SUCC/blob/main/addons/SUCC/scripts/succ.gd)). An "apex" preset would slot naturally into that system. Unity's nearest equivalent, **Olezen/UnitySourceMovement** (MIT, 389 stars), is a port of the Fragsurf controller with its own collision-trace code, but its last commit was in March 2020 ([UnitySourceMovement](https://github.com/Olezen/UnitySourceMovement)). Unity's built-in `CharacterController` supports only a capsule shape and has no velocity model ([Unity manual](https://docs.unity3d.com/6000.3/Documentation/Manual/class-CharacterController.html)). Godot's `CharacterBody3D` stores a velocity and exposes settings for floor snapping, slide iterations and slopes ([CharacterBody3D](https://docs.godotengine.org/en/stable/classes/class_characterbody3d.html)). Bots can run the same movement code driven by AI input. In both engines that costs one collision solve per bot per tick.

### Projectiles and recoil are math, not engine features

The best way to model bullets with travel time and drop is analytically: position plus velocity under gravity, advanced on a fixed tick. Each tick, cast a line segment from the bullet's previous position to its new one. That catches fast bullets without rigid bodies or continuous collision detection, in either engine. Unity has a structural advantage at high bullet counts, because `RaycastCommand` batches every live bullet's cast into one multithreaded job ([RaycastCommand](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/RaycastCommand.html)). Godot has no batched query, and its docs say the physics world can only be queried safely during `_physics_process` ([Godot ray-casting](https://docs.godotengine.org/en/stable/tutorials/physics/ray-casting.html)).

Since 4.6, Godot's default physics engine for new 3D projects has been **Jolt** ([Godot 4.6 release](https://godotengine.org/releases/4.6/)). Jolt's collision margins round off the edges of box shapes and "can sometimes result in odd collision normals when performing shape queries" ([Jolt in Godot docs](https://docs.godotengine.org/en/stable/tutorials/physics/using_jolt_physics.html)). That matters here: each dummy's chest, stomach, pelvis and feet hitboxes are boxes (5 of the 17). The fix is either to lower Jolt's margin setting or to keep the physics engine out of hit tests altogether (see the risks section).

Recoil patterns are data plus a per-frame offset to the view angles, so nothing about them depends on the engine. An open-source Godot 4 FPS template already models per-weapon spray profiles and keeps hitscan and projectile logic in separate components ([chafmere/Godot4-FPS-Template](https://github.com/chafmere/Godot4-FPS-Template)).

### Your bot files import into Godot nearly ready to shoot

Here Godot's lead is unambiguous. Since 4.4, its glTF importer stores each node's extras as metadata that code can read with `get_meta("extras")` ([PR #86183](https://github.com/godotengine/godot/pull/86183)). When a non-bone node is parented to a bone, which is exactly how your `HB_` hitboxes are built, the importer creates a `BoneAttachment3D` under the skeleton that follows that bone through every animation ([gltf_document.cpp at 4.7.2](https://github.com/godotengine/godot/blob/4.7.2-stable/modules/gltf/gltf_document.cpp)). A short post-import script ([Godot import configuration](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/import_configuration.html)) can then replace each `HB_` mesh with a collision shape sized from its extras. Each of your 17 hitboxes sits on a different bone, so the importer's habit of reusing one attachment per bone will not merge any of them. The repo's `dummy_medium.glb` has already loaded and rendered in Godot inside the agent's container; the first import took 9.4 s.

Unity has no built-in glTF importer. The official glTFast package recreates the node hierarchy and the skin. It reads extras only through an add-on API that uses the Newtonsoft JSON parser, and the documentation shows only a runtime-import example ([glTFast custom extras](https://docs.unity3d.com/Packages/com.unity.cloud.gltfast@6.9/manual/UseCaseCustomExtras.html)). Its Mecanim animation import is also partial: clips "won't be assigned and cannot be played back without further work" ([glTFast features](https://docs.unity3d.com/Packages/com.unity.cloud.gltfast@6.9/manual/features.html)). Unity remains workable because your art pipeline already writes a JSON sidecar for engines whose importer drops extras. An editor script can read that sidecar and add colliders to the matching nodes by name. That is extra glue code, not a blocker.

Both engines share one trap: hitboxes are only accurate if the bones update before hits are tested. By default, Godot's `Skeleton3D` updates its bone modifiers on the render frame, not the physics tick ([Skeleton3D](https://docs.godotengine.org/en/stable/classes/class_skeleton3d.html)). Unity needs `Physics.SyncTransforms` after animation if you test hits in `Update`. Its animator culling option (`CullUpdateTransforms` or `CullCompletely`) also freezes the bones of off-screen bots unless you set it to `AlwaysAnimate` ([SyncTransforms](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Physics.SyncTransforms.html), [AnimatorCullingMode](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/AnimatorCullingMode.html)).

## Unity's strongest case is precedent, assets and C# fluency

The best argument for Unity is that the market leader already proves it works. **Aimlabs, with more than 45 million registered players, is built on Unity** and ships on PC, Xbox and PS5 ([Wikipedia: Aimlabs](https://en.wikipedia.org/wiki/Aimlabs)). Escape from Tarkov, BattleBit Remastered and Ultrakill show that Unity handles shooters. No Godot aim trainer has shipped commercially. Godot's precedents are open-source hobby trainers such as LibreAim and VANTA ([LibreAim](https://github.com/Nokorpo/LibreAim), [VANTA](https://github.com/aimtrainer-code/aim-trainer)), plus one strong solo FPS: **Road to Vostok, which sold over 180,000 copies in its first week** after being ported from Unity to Godot ([Wikipedia: Road to Vostok](https://en.wikipedia.org/wiki/Road_to_Vostok)). Among Steam games that have earned more than $500K, 53.7% use Unity and 4.1% use Godot ([GameDiscoverCo](https://newsletter.gamediscover.co/p/hows-pc-game-engine-usage-changing)).

The ecosystem gap is wide. One secondary source counts **over 80,000 Unity Asset Store items against about 3,000** in Godot's library ([Tech Insider](https://tech-insider.org/godot-vs-unity-engine-2026/)), and FPS tutorials are still far more plentiful for Unity. For an AI agent, the gap in training data may matter even more. Stack Overflow holds 1.62 million `c#` questions and 76,766 `unity-game-engine` questions, against 2,417 `godot` and 1,155 `gdscript` questions ([Stack Exchange API](https://api.stackexchange.com/2.3/tags/gdscript/info?site=stackoverflow)). AI models still write Godot 3 syntax (`yield`, `KinematicBody`, `export var`) in Godot 4 projects ([Surmado](https://www.surmado.com/blog/ai-mistakes-in-godot-4-code)). What softens this is that Godot 4's parser rejects that syntax immediately. During the research, a Godot 3 `yield` failed a `--check-only` run in 0.17 s with the message "'yield' was removed in Godot 4. Use 'await' instead". The errors are therefore caught by the agent's own checks before they ever reach you. Godot also supports C#, which would recover the C# training-data advantage. The cost is a separate .NET editor build, the .NET SDK and extra build time ([Godot C# basics](https://docs.godotengine.org/en/stable/tutorials/scripting/c_sharp/c_sharp_basics.html)).

Cost and Steam support do not separate the two engines for this project. Unity Personal is free up to **$200K in combined revenue and funding** over 12 months, and the Unity splash screen has been optional since Unity 6. Above that threshold, Unity Pro costs **$2,310 per seat per year** in 2026, after price rises of 8% in 2025 and 5% in 2026 ([Unity pricing updates](https://unity.com/products/pricing-updates), [Wikipedia: Unity Technologies](https://en.wikipedia.org/wiki/Unity_Technologies)). The 2023 per-install Runtime Fee was cancelled in September 2024. Godot is MIT-licensed with no fee at any revenue level. Both engines have free, MIT-licensed Steamworks wrappers with leaderboards, stats and Workshop support: GodotSteam and Steamworks.NET ([GodotSteam](https://godotsteam.com/), [Steamworks.NET](https://steamworks.github.io/)). Steam's $100 per-app fee is the same either way ([Steam Direct](https://partner.steamgames.com/steamdirect)).

Unity the company lost $401.5M on $1.85B of revenue in 2025, after repeated rounds of layoffs, yet engine releases have kept a steady schedule ([Wikipedia: Unity Technologies](https://en.wikipedia.org/wiki/Unity_Technologies)). Godot's development fund shows €35,434 a month in recurring donations ([Godot Development Fund](https://fund.godotengine.org/)). Because Godot is MIT-licensed, a fork can carry on even if its foundation fails.

Unity would become the better choice under different circumstances. One case is development moving to a Windows workstation with a GPU, where a human drives the editor. Another is a plan to release on consoles with outside funding: Unity Pro supports consoles directly, while Godot needs third-party porting companies ([Godot console support](https://godotengine.org/consoles/)). A third is Unity 7's free CLI and MCP tools, due in 2027, turning out to close the gap for headless agents.

## Eight risks in the Godot plan, and how to defuse each

The biggest risks of choosing Godot sit on exactly the hardware this audience owns. Most of them can be designed around from day one instead of being discovered late.

| Risk | Why it matters | Mitigation |
|---|---|---|
| Menu freezes with a visible cursor in 4.7.2 ([#122779](https://github.com/godotengine/godot/issues/122779)) | High-polling mice could freeze menus for seconds | Keep the mouse captured everywhere and draw your own cursor from raw counts, which also keeps menus 1:1. Check it in test 4. Pin the engine version and upgrade once the issue is resolved |
| The agent writes Godot 3 code | Wasted iterations and subtle misuse of the API | A project `CLAUDE.md` that lists Godot 4 idioms, static typing, and `--check-only` plus headless tests on every change |
| GDScript is slow in hot loops | Bots × 17 hitboxes × projectiles must fit in about 2 ms at 480 Hz | Analytic bullets and hit tests. Profile in test 6. Move hot loops to C# or a C++ GDExtension only if profiling demands it |
| The render queue cannot go below 2 frames, and there is no Reflex support | Possibly one more frame of latency than Unity set to a queue of 1 | Use a two-image swapchain, exclusive fullscreen, and either uncapped FPS or the VRR cap. Measure against Apex in test 5 |
| Physics queries only work during the physics step, and Jolt rounds box edges | Hit tests and aim-assist checks lag behind rendered frames or miss the corners of chest and pelvis boxes | Test rays analytically against the sidecar's capsules and boxes using bone transforms, or lower Jolt's collision margin |
| Hitboxes one frame behind the animation | Shots near the edge of a limb register wrongly | Switch bot skeletons to physics-step updates, or run analytic tests after animation. Never apply physics interpolation to the camera |
| The gyro API is experimental and untested on DualSense | Gyro aiming may need workarounds | Check it in test 7. Community DualSense extensions such as [Godot-Dualsense](https://github.com/rafaelvaloto/Godot-Dualsense), which also cover adaptive triggers, are the fallback |
| The agent cannot feel the game | Latency, feel and frame pacing only show up on your PC | Build telemetry from day one, so every build writes logs you can send back. Use Xvfb screenshots for visual checks |

**Analytic hit testing.** Two of these mitigations deserve emphasis, and this is the first. The hitbox sizes and bone offsets already live in your JSON sidecar. Code can intersect a ray directly with each capsule and box, using the current bone transforms. That removes three problems at once: the rule that queries only run during the physics step, Jolt's rounded margins, and per-query engine overhead. The same code can serve aim assist's target checks on every rendered frame, which is where mouse-look and stick input have to run. Analytic hit testing is usually saved as a late optimisation for when bone colliders get expensive. For this trainer, adopting it from the start removes more problems than it adds, and it is plain math the agent can unit-test in the container.

**Telemetry.** The second key mitigation is to treat your Windows PC as the only place where feel and latency can be judged. Every build should be able to write a frame-time CSV and a mouse-count log, along with a dump of the active settings, that you send back to the agent. That turns each of your play sessions into data the agent can act on, instead of impressions it has to guess from.

## Seven tests in the first week decide whether to continue

Before committing, run a one-week spike: the agent builds a bare test project, and you run it on your gaming PC. While the agent builds it, it should also write the core math as pure functions with unit tests from day one: sensitivity conversion, the ballistic step, recoil playback, stick response curves and aim-assist strength. That code is identical in any engine, which keeps the decision reversible. The pass thresholds below are suggestions from this report, not published standards.

| # | Test | Where | How | Suggested pass threshold |
|---|---|---|---|---|
| 1 | Toolchain and bot import | Agent's container | Pin Godot 4.7.2 in a setup script. Import all three dummies. A headless test compares every `HB_` node's extras and bone with the JSON sidecar. Then export the `.exe` | All 51 hitboxes match the sidecar, and the export finishes without errors |
| 2 | Launch | Your PC | Run the `.exe` in exclusive fullscreen on D3D12, then on Vulkan | It starts and reports your monitor's actual refresh rate |
| 3 | Sensitivity exactness | Your PC | A debug overlay shows the summed `screen_relative` counts and the degrees turned. Set the same sensitivity and DPI as in Apex. Measure the mouse distance for a full 360° turn in the Firing Range and in the build, five times each | Degrees turned equal counts × the code's formula exactly, and the average 360° distance matches Apex to within your hand's repeatability (about 2%) |
| 4 | Polling stress | Your PC | Set the mouse to 1, 2, 4 and 8 kHz. Try gameplay (captured mouse) and a menu (visible cursor), each with V-Sync off and with the VRR cap. The build logs frame times to CSV | In gameplay, 1% lows stay at or above your refresh rate at every polling rate. In menus, no frame takes longer than 100 ms |
| 5 | Click-to-photon latency | Your PC | Film the mouse click and the muzzle flash with phone slow-motion (240 FPS), at least 20 clicks per setting, in both the build and Apex. Compare a swapchain of 2 against 3, and V-Sync off against the VRR cap | The build's median latency is no worse than Apex's on the same PC |
| 6 | Bot and projectile load | Your PC | 30 animated dummies (17 hitboxes each), 500 projectiles per second, aim assist on, frame rate uncapped | 1% lows stay at or above your monitor's refresh rate |
| 7 | Controllers | Your PC | Xbox pad and DualSense, over USB and Bluetooth, with Steam Input on and off. On-screen readouts for raw axes and gyro, plus a rumble test | Sticks reach ±1.0 with no engine deadzone, the DualSense gyro reports values, and rumble works |

The spike should start from the settings the research supports. Keep the mouse captured and read aiming from `screen_relative`. Leave `use_accumulated_input` on, since it sums counts without losing any ([Input class](https://docs.godotengine.org/en/stable/classes/class_input.html)). Apply camera rotation in `_process`, never on the physics tick, and keep physics interpolation off the camera. Set `swapchain_image_count` to 2 and use exclusive fullscreen. Raise the physics rate to 120–240 ticks per second, which Godot's docs suggest for reducing physics-related input latency ([Godot jitter and input-lag docs](https://docs.godotengine.org/en/latest/tutorials/rendering/jitter_stutter.html)).

Failures in tests 1, 3 and 7 have fallbacks that work in any engine: the sidecar, pure-code math, and the community DualSense extensions. Only a failure in test 4 or 5 should reopen the engine decision, and even then switching is not automatically better, because Unity has its own unresolved 8 kHz problem. The order of escalation is to adjust settings first, then try the Godot 4.8 development builds, then patch the MIT-licensed engine. Only after all three should you rebuild the same test scene in Unity on a Windows machine and measure it under identical conditions.

## Conclusion

For this project the engine question turned out to be about who can check the work, not about runtime speed. At runtime the engines differ by settings and a few months of bug fixes. In the development loop they differ by orders of magnitude: a 0.27-second headless test against an editor boot with a licence check, and a screenshot the agent can render itself against none at all. The 8 kHz mouse problem is a Windows behaviour that every engine inherits, and Godot's lead there is a fix only weeks old with a fresh regression report against it. That lead is a reason to test, not a guarantee, and it is why the first week belongs on your PC rather than in the agent's container.

The deeper implication is about the architecture of the work. The agent is the factory and your gaming PC is the only lab, so the builds have to measure and report on themselves. Most of what makes this an *Apex* trainer is math that has no engine in it: sensitivity conversion, ballistics, recoil playback, stick curves and aim assist. Keeping that math in pure, tested functions makes the Godot decision cheap to reverse, whether Godot's risks materialise or Unity 7's 2027 promises arrive.
